# Form prefill and submitted values

Use this reference when working with generated form markup, prefilled fields, unmapped questions, or values consumed after a form submission. It intentionally covers form behavior and integration only; it does not document Dataverse table, column, relationship, security-role, or CRM administration.

Official references: [Form prefill](https://learn.microsoft.com/en-us/dynamics365/customer-insights/journeys/real-time-marketing-form-prefill), [unmapped fields](https://learn.microsoft.com/en-us/dynamics365/customer-insights/journeys/real-time-marketing-forms-custom-fields), and [submitted values](https://learn.microsoft.com/en-us/dynamics365/customer-insights/journeys/real-time-marketing-form-submitted-values).

## Form prefill

Form prefill is a platform feature, not a client-side data-fetching pattern. A Customer Insights - Journeys tracking link can add an `msdynmkt_prefill` token to the URL. The form service uses that token and the visitor's tracking consent to populate known Contact or Lead values.

Important behavior:

- The token is valid for 30 days and is generated by a real Customer Insights - Journeys journey link. Do not manufacture, persist, log, or expose prefill tokens in custom JavaScript.
- Prefill works for marketing and event registration forms, but not for Customer Insights - Data profile audiences. Preference centers use a different prefill mechanism.
- Enabling prefill in the form editor enables it for the form; individual fields can then opt out. Preserve the generated `data-prefill` and target-audience metadata.
- A field is prefilled only when its target audience matches the recognized record. `Contact` fields do not prefill for leads; `Lead` fields do not prefill for contacts; `Lead & Contact` fields prefill only for contacts.
- A read-only prefilled field can display known information without allowing the visitor to edit it. Do not treat read-only or prefilled values as a security boundary.
- A forwarded email link can expose personal information. Tell users not to forward links containing prefilled forms.

Add the hosting domain to the allowed-domain list and enable external form hosting so forms and prefill can use it. Full email-domain authentication is not required solely for forms or prefill. Do not work around the hosting check with JavaScript or by copying values into query parameters.

### Consent checkbox behavior

Prefill also calculates consent checkbox state from the current consent decision and the checkbox's **When checked** setting. With **Opt user in**, checked means the resolved decision is **Will send**. With **Opt user out**, the displayed state is inverted. A checkbox covering multiple channels can result in consent for all linked channels when submitted, so review the generated consent configuration before changing its markup.

### Prefill troubleshooting

Check these in order:

1. Open the page from a tracking link generated by a real journey, not a test-send link.
2. Confirm the URL contains the tracking context and `msdynmkt_prefill` parameters.
3. Confirm form-level and field-level prefill are enabled.
4. Confirm the visitor has the required Tracking consent.
5. Confirm the field's generated target audience matches the recognized Contact or Lead.
6. Test the published form, not only the Designer preview.

## Unmapped form fields

Use an unmapped field for a question whose answer should be submitted with the form but should not update a Lead or Contact attribute. Add it through the form editor's **Elements** panel. Do not create a fake mapped input or add the field only after rendering with DOM manipulation.

Unmapped fields:

- Store their submitted values with the form submission rather than in a Lead or Contact record.
- Have a logical name used as the submitted-value key. Only one field with a given logical name can be used in a form.
- Can be short text, long text, option set, multi-select, radio button, number, checkbox, or date/time controls.
- Support normal form-editor properties such as label, placeholder, default value, required state, hidden state, and custom validation.
- Must remain present in the stored form HTML. A field created only after the form has rendered may not be processed by backend validation.

Hidden fields are still submitted data. Never place secrets, access tokens, or authorization decisions in an unmapped or hidden field.

## Use submitted values

Submitted values from both mapped and unmapped fields can be consumed by the **Marketing Form Submitted** trigger. This is downstream journey/email behavior, not a replacement for server-side validation.

For branching:

- Use the field's logical name to identify the correct submission.
- Use the raw field value for option sets, multi-selects, and two-option fields when the stored numeric value is required.
- Filter to the latest field submission when multiple submissions could be present.
- Do not compare an option-set label such as `Blue` to a numeric stored value such as `1` without checking which property the condition exposes.

For email personalization, submitted values can provide dynamic text or a summary list, including in double opt-in scenarios where a Contact or Lead record may not yet be available. Confirm the current localized-value behavior for unmapped option fields before relying on display labels; platform documentation has changed this behavior over time.
