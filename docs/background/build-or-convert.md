# Build or convert a form

Use this reference for the end-to-end decision and acceptance workflow. It separates what an agent can check in code from what only the target Customer Insights - Journeys environment can prove.

## Decide what is being converted

Use one path only:

| Requirement | Path | Source of environment values |
| --- | --- | --- |
| New form owned and rendered by Customer Insights | Native form | Blank form or template created in the target environment |
| Existing design can be rebuilt with supported form fields and elements | Native rebuild | Same-environment blank form plus the existing HTML/CSS as a visual reference |
| Existing DOM or complex client logic must remain | Form Capture | Capture snippet generated after publishing a matching Customer Insights form |
| Existing form must also submit to another platform | Form Capture with deliberately tested dual submission | Generated capture snippet plus the existing submission contract |
| Site only needs to show a Customer Insights form | Standard JavaScript embed | Embed snippet generated by **Publish** |

Microsoft recommends the native form editor when an existing form can be recreated there. Form Capture is intended for complex existing forms or forms that also send to other systems.

## Required inputs

Do not begin a deployable implementation without these inputs:

- form type and target audience;
- matching strategy and its required fields;
- intended mapped and unmapped questions;
- target-environment form HTML, embed snippet, or capture snippet;
- compliance profile and configured consent requirements;
- hosting domain and publishing model;
- existing form behavior when converting, including its action, validation, redirect, CAPTCHA, analytics, and other destinations.

When an input is unavailable, mark it as a blocker in the handoff and provide only a candidate implementation. Never hide the gap by copying an identifier from an example.

## Map fields before changing markup

Create an explicit mapping inventory:

| Existing control | Destination | How to implement |
| --- | --- | --- |
| Contact or Lead attribute | Mapped field | Add the attribute from the selected audience in the form editor |
| Question that must be available on the submission but not update a record | Unmapped field | Add a supported unmapped field in the form editor |
| Purpose or topic consent | Consent element | Configure it in the target form editor; never infer IDs from labels |
| Bot protection | reCAPTCHA | Add and configure the form-editor reCAPTCHA element for public native forms, or preserve and validate the existing CAPTCHA before a capture submission |
| Hidden business value | Hidden mapped or unmapped field | Treat it as user-controlled data; do not store secrets or authorization decisions |
| Unsupported control or complex behavior | Rework or Form Capture | Do not disguise it as a mapped field by hand-authoring `data-*` attributes |

The platform validates matching-rule fields when publishing. Email is the default matching field in Microsoft's standard Contact example, but the actual required set comes from the selected matching rule and target table. Required Dataverse attributes can also produce nonblocking warnings. Do not make last name or any other field universally required solely because it appears in this repository's fixtures.

## Native form from scratch

1. Create the form in **Customer Insights - Journeys** > **Channels** > **Forms** and choose a blank form when no target-environment template is required.
2. Confirm the target audience before adding fields. Field availability and mappings are audience-specific.
3. Add mapped fields from **Fields** and unmapped questions, content, layout, consent, reCAPTCHA, and Submit from the supported editor panels.
4. Configure field required state and validation through the field properties. Ensure all matching-rule fields are present and required.
5. Configure the duplicate-record strategy, post-submission action, prefill, web tracking, and consent intentionally.
6. Use Theme before custom CSS. Use the HTML editor only for a requirement the form editor cannot satisfy.
7. Run the local checker on any exported or edited source, then paste or save it into the same environment. Run **Check content**.
8. Publish to a standalone page or use the exact generated JavaScript embed. For an external page, add the domain to allowed domains and enable external form hosting.
9. Submit a uniquely identifiable test record and inspect both the form submission state and the target record.

New forms use the table-less, `div`-based layout by default in current releases. Existing forms are converted to that layout when edited and saved. Treat older table-based examples as archival exports, not the preferred starting point.

## Rebuild existing HTML as a native form

1. Preserve the original file as a comparison artifact.
2. Create a blank form in the target environment and export or inspect its stored HTML. This supplies the current document envelope and generated form conventions.
3. Port semantic content, layout, and scoped visual rules. Avoid copying global host-page CSS that can affect the form loader, tables, controls, or accessibility.
4. Replace every original input intended for Customer Insights processing with a field added in the form editor. Use an unmapped field when no Contact or Lead attribute should be updated.
5. Add consent and reCAPTCHA through the editor. Remove old HIP CAPTCHA markup; it no longer provides bot protection.
6. Retain the current environment's generated block metadata, validation, IDs, and form envelope. The drag-and-drop meta tag and `data-container`/`data-editorblocktype` attributes enable Designer features, but they do not create valid field mappings by themselves.
7. Run the local checker, **Check content**, published responsive and accessibility checks, and an end-to-end submission.

An arbitrary external document can be pasted into the HTML editor and displayed in the simplified full-page editor. Add the documented Designer meta tag and containers only when drag-and-drop editing is required. Do not assume that doing so maps ordinary HTML controls to Contact or Lead attributes.

## Platform acceptance and end-to-end checks

The local checker catches structural mistakes and unsafe placeholders. It cannot validate Dataverse metadata, matching rules, consent configuration, the domain allow-list, platform sanitization, or submission processing.

Before calling the form compatible, confirm:

- the form saves in the target environment;
- **Check content** has no blocking errors;
- warnings about required target attributes are understood and resolved when relevant;
- the published form renders on the intended domain and at narrow/mobile widths;
- labels, required states, keyboard navigation, focus, error messages, and reCAPTCHA work;
- no unintended horizontal overflow is introduced after published inline styles are applied;
- a unique test submission reaches **Success**;
- the correct Contact or Lead is created or updated under the chosen matching strategy;
- mapped and unmapped values are present where expected;
- purpose/topic consent records match the configured checkbox behavior;
- redirects occur only after the submission has completed.

For standalone pages, changed content can remain cached for up to 10 minutes. Append `#d365mkt-nocache` only to a test URL when checking the latest published version.
