# Form Capture

Use Form Capture to route an existing website form's submission into Customer Insights - Journeys without replacing its DOM. Prefer a native Customer Insights form when the existing form can be recreated in the form editor.

Official references reviewed through Microsoft Learn MCP on 2026-08-23:

- [Capture forms in Customer Insights - Journeys](https://learn.microsoft.com/dynamics365/customer-insights/journeys/real-time-marketing-form-capture)
- [Deploy pages that contain Customer Insights - Journeys forms](https://learn.microsoft.com/dynamics365/customer-insights/journeys/real-time-marketing-deploy-pages)
- [Forms security and privacy](https://learn.microsoft.com/dynamics365/customer-insights/journeys/real-time-marketing-form-security-privacy)

## Preconditions

- Customer Insights - Journeys is current enough to include `DynamicsMKT_Forms` solution version `1.1.35355` or later.
- **Settings** > **Feature switches** > **Forms** > **Form capture** is enabled.
- The existing form's domain is in the allowed-domain list with external form hosting enabled. Full email-domain authentication is not required merely to host or prefill forms.
- The agent has the capture snippet generated by the target environment. Do not recreate its loader URL, form ID, or API URL from memory.

## Generate the capture contract

1. Create a form in Customer Insights - Journeys and select the correct audience.
2. Add every mapped field that the existing page must send. A mapping in JavaScript does not update a Contact or Lead field unless that field is also present in this Customer Insights form.
3. Add supported unmapped fields for submission-only values.
4. Configure purposes and topics in the form editor. Consent-definition edits made only in the capture code are ignored.
5. Add Submit so the Customer Insights form can pass validation, publish it, and copy the generated Form Capture snippet.
6. Replace every `***Please fill***` marker in the generated template with a value derived from the existing form or target environment.

## Integrate the existing form

Keep the generated `FormCapture.bundle.js` URL and `captureConfig`. Adapt only the selectors, mappings, validation coordination, success handling, and existing-site behavior.

The generated pattern uses:

- `d365mktformcapture.waitForElement()` to obtain the form, including dynamically rendered forms;
- `d365mktformcapture.serializeForm(form, mappings)` to build the payload;
- mapping objects with `FormFieldName` and `DataverseFieldName`, plus generated value mappings when required for options, multi-selects, lookups, or consent;
- `d365mktformcapture.submitForm(captureConfig, payload)`, which returns a promise.

Run the local preflight when the integrated page is available. The command below assumes the skill directory is the current directory:

```bash
python3 scripts/validate_form.py path/to/page.html --mode capture
```

The checker cannot verify that a logical name exists in the selected audience or that a purpose/topic belongs to the configured compliance profile. The target environment and a real submission must prove those relationships.

## Submission ownership

Choose one behavior deliberately:

- **Customer Insights only:** prevent the original submission, validate the form, await `submitForm`, then show success or redirect.
- **Dual submission:** coordinate the existing destination and Customer Insights independently. Define what the user sees if only one succeeds, and make retries idempotent where possible.

Do not redirect immediately after starting `submitForm`; navigation can cancel the pending request. If an existing validator or CAPTCHA cancels the native submit event, do not call Customer Insights. Check `event.defaultPrevented` or invoke capture only after the existing validation succeeds.

Avoid automatic retry loops. They can create duplicate records or duplicate consent updates. Preserve the original form's accessible error summary and focus behavior when adding capture errors.

## Limitations

- Form Capture does not collect form-visit events and web tracking is unavailable in capture scenarios.
- It requires developer maintenance and is more complex than embedding a native Customer Insights form.
- Existing hidden fields and mapping values are attacker-controlled input.
- Consent still comes from the Customer Insights form-editor configuration, not from arbitrary labels or IDs in the site markup.
- A successful browser promise does not prove the target record and consent processing completed correctly; inspect the form submission and target data.

## Acceptance checks

Use a non-production form and a unique test value. Confirm:

1. the existing validation and CAPTCHA reject invalid input without calling `submitForm`;
2. every mapped control serializes the intended value, including options, multi-selects, lookups, and unmapped fields;
3. the Customer Insights submission reaches **Success**;
4. the intended Contact or Lead create/update behavior matches the selected audience and matching rule;
5. consent records match the form-editor configuration;
6. the original destination still succeeds when dual submission is required;
7. redirects and success messages occur only after the required destination or destinations complete;
8. failures are visible, recoverable, and do not trigger duplicate automatic submissions.
